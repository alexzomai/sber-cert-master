# Установка sber-cert-master агентом

Инструкция для ИИ-агента (Claude Code, Codex и т. п.), который сам ставит службу на машину, откуда агенты ходят в Sber API. Шаги идут по порядку. Каждый шаг заканчивается проверкой: не переходите дальше, пока она не прошла.

Отметка **[ЧЕЛОВЕК]** означает шаг, который агент сделать не может или не должен: в нём есть секреты, вход в СберБизнес или права root. На таком шаге остановитесь и попросите человека, точно указав, что нужно и куда это положить.

## Правила безопасности (обязательно)

- **Никогда** не печатайте, не логируйте и не коммитьте `client_secret`, `refresh_token`, `access_token`, пароль `.p12` и закрытый ключ. Не передавайте их в аргументах команд: аргументы видны в `ps` и в истории. Секреты передаются только через файлы с правами `0600` или через stdin.
- Не вызывайте вручную `/oauth/token`, `/change-client-secret` и `/refresh-client-secret`. Это делает только служба. Лишний refresh или смена секрета ломают доступ.
- Перед командами с секретами выключайте трассировку оболочки (`set +x`).
- Не передавайте токен в аргументах `curl` (`-H "Authorization: ..."`): подавайте заголовок через stdin (`-H @-`) и ставьте `-q` первым ключом (иначе `~/.curlrc` с трассировкой может записать заголовок в лог), как в примерах ниже.
- Временные файлы держите в `$TMPDIR` или `~/.cache/agent-tmp`, не в `/tmp`. После `init` удалите файлы с секретами (`shred -u`, если доступен).

## 0. Предварительная проверка

```sh
python3 -c 'import sys, ssl, tomllib, fcntl; assert sys.version_info >= (3, 11), sys.version'
openssl version
systemctl --version | head -1
curl -sS -o /dev/null -w '%{http_code}\n' --max-time 30 https://developers.sber.ru/
```

Больше ничего не требуется: служба написана на стандартной библиотеке Python, установщик только копирует файлы. `pip`, `venv` и доступ к индексу пакетов не нужны; доступ в интернет нужен только к хостам Сбера.

Если служба уже установлена, не ставьте её заново. Узнайте, где остановилась прошлая установка:

```sh
# system (от root или через sudo):
sudo -u sber-cert-master env SBER_CERT_MASTER_CONFIG=/etc/sber-cert-master/config.toml sber-cert-master status
systemctl is-active sber-cert-master
# user:
SBER_CERT_MASTER_CONFIG=~/.config/sber-cert-master/config.toml sber-cert-master status
systemctl --user is-active sber-cert-master
```

Куда продолжать (проверяйте строки сверху вниз, берите первую подходящую):

| Что показывают `status` и `systemctl` | Продолжить с |
|---|---|
| команды `sber-cert-master` нет, или в режиме system у агентов нет `PROCESS-OK` (шаг 1) | шаг 1 |
| профиля нет / `initialized: False` | шаг 2; если конфиг готов — сразу «Предпроверка» в конце шага 2. К шагу 3 — только после `PREFLIGHT-OK` в этой сессии |
| `refresh_token_age_days` — число (refresh_token сохранён, неважно, импортом или `exchange-code`, и неважно, истёк ли access_token), служба **не** `active` | **немедленно шаг 7**: сначала запустить службу (`systemctl enable --now ...`), потом переключить агентов, если ещё не переключены. Старый токен агентов уже отозван, а служба сама получит свежий, как только запустится — повторная авторизация не нужна |
| `refresh_token_age_days: None` и `import_pending: True` | шаг 6 — повторите импорт **тем же** файлом (ответ банка на прошлую попытку не получен) |
| `refresh_token_age_days: None`, импорта не было (например, откат после `init`) | заново: «Предпроверка» шага 2 → шаги 3–6. Повторный `init` в шаге 5 перезапишет профиль (в нём нет гранта, терять нечего) свежими материалами; `--force` не нужен |
| служба `active`, но агенты ещё на старой конфигурации | шаг 7: ворота `ready`, затем п. 2 (переключить агентов) |
| служба `active`, агенты читают файлы службы | шаг 8 |

## 1. Выбор режима

| Режим | Когда | Скрипт | Конфиг | Каталог для агентов | Каталог для исходных секретов |
|---|---|---|---|---|---|
| system (рекомендуется) | есть root; агенты работают под разными пользователями | `sudo ./deploy/install.sh` **[ЧЕЛОВЕК, если у агента нет sudo]** | `/etc/sber-cert-master/config.toml` | `/var/lib/sber-cert-master/public/<profile>/` | `/var/lib/sber-cert-master/incoming/` (0700, только служба) |
| user | root нет; агенты работают под тем же пользователем | `./deploy/install-user.sh` | путь печатает установщик (обычно `~/.config/sber-cert-master/config.toml`) | `~/.local/state/sber-cert-master/public/<profile>/` | `~/.cache/agent-tmp/sber-init/` (0700) |

```sh
git clone <repo> sber-cert-master && cd sber-cert-master   # или уже в каталоге проекта
python3 -m unittest discover -s tests                        # должно быть OK
./deploy/install-user.sh                                     # или: sudo ./deploy/install.sh
# system с собственной группой агентов (выберите её ДО установки):
#   sudo env AGENT_GROUP=<группа> ./deploy/install.sh
# установщик добавит в неё пользователя службы и запишет её в publish_group конфига
```

Дальше в инструкции:

```sh
# user: возьмите строку `export SBER_CERT_MASTER_CONFIG=...` из вывода install-user.sh
#       (при нестандартном XDG_CONFIG_HOME путь отличается от ~/.config; тот же путь записан в юниты)
export SBER_CERT_MASTER_CONFIG=~/.config/sber-cert-master/config.toml
D=~/.cache/agent-tmp/sber-init; install -d -m 0700 "$D"
# system:
# export SBER_CERT_MASTER_CONFIG=/etc/sber-cert-master/config.toml
# D=/var/lib/sber-cert-master/incoming
```

В режиме system все команды `sber-cert-master`, кроме `token`, выполняйте от пользователя службы: `sudo -u sber-cert-master env SBER_CERT_MASTER_CONFIG=/etc/sber-cert-master/config.toml sber-cert-master ...`. Исходные файлы кладите именно в `/var/lib/sber-cert-master/incoming/`: домашний каталог другого пользователя служба прочитать не сможет.

**Только режим system — доступ агентов к каталогу публикации (обязательно сейчас, до шага 3).** Каталог `<publish_dir>/<profile>/` (права 0750) доступен только группе из `publish_group` в конфиге (по умолчанию `sber-agents`). Группу выбирают при установке (`AGENT_GROUP`); в командах ниже подставьте её вместо `sber-agents`. В этой же группе должен состоять пользователь службы — установщик добавляет его сам. Если вы меняете `publish_group` в уже установленной службе, выполните `sudo usermod -a -G <группа> sber-cert-master` **[ЧЕЛОВЕК]**, перезапустите службу и повторите для агентов проверки этого шага и шага 8 (служба при следующей публикации переведёт на новую группу действующие файлы: каталог профиля, токен, `env`, `ca-bundle.pem` и текущий каталог `tls`); затем убедитесь, что каждый агент выполнил запрос к банку; иначе любая команда `sber-cert-master` сразу сообщит, что служба не состоит в группе публикации.

1. Добавьте в группу каждого пользователя, от которого работают агенты: `sudo usermod -a -G sber-agents <user>` **[ЧЕЛОВЕК]**.
2. Новое членство получают только процессы, запущенные **после** этого из нового сеанса. Перезапустите агента так, чтобы обновился его набор групп:
   - системная служба (`systemctl restart <unit>`) — достаточно перезапуска юнита;
   - служба `systemd --user` (в том числе с linger) — перезапуска юнита **недостаточно**: менеджер пользователя сохраняет старые группы. Перезапустите сам менеджер: `sudo systemctl restart user@$(id -u <user>).service` **[ЧЕЛОВЕК]** (это перезапустит все пользовательские службы этого пользователя);
   - агент в терминале/tmux — завершите сеанс входа и войдите заново (или запустите агента через `sudo -u <user> -i`).
3. Проверьте группу **у работающего процесса каждого агента** — точным совпадением числового GID, а не у нового `sudo -u`:

```sh
G=$(getent group sber-agents | cut -d: -f3)
for pid in <pid агента> ...; do
  awk -v g="$G" '$1=="Groups:" { for (i = 2; i <= NF; i++) if ($i == g) ok = 1 } $1=="Gid:" && $5 == g { ok = 1 } END { exit !ok }' \
    "/proc/$pid/status" && echo "PROCESS-OK $pid" || echo "НЕТ ГРУППЫ У ПРОЦЕССА $pid"
done
```

Проверка: `sber-cert-master --version` печатает версию; в режиме system для **каждого работающего процесса агента** получено `PROCESS-OK`. Пока хотя бы у одного «НЕТ ГРУППЫ», не переходите к шагу 3: такой агент после отключения собственного обновления не сможет прочитать токен службы.

### Режим Docker

Если агенты работают в контейнерах, служба тоже ставится контейнером: образ `deploy/docker/Dockerfile`, пошаговый порядок — в комментарии в начале `deploy/docker/compose.example.yaml` (копируйте его в `compose.yaml` и вызывайте `docker compose -f compose.yaml ...`). Отличия от режима system:

- секреты лежат в томе `sber-state`; в контейнеры агентов подключается **только** том `sber-public`, **только на чтение** и **по тому же пути** `/var/lib/sber-cert-master/public`, что и у службы: тогда абсолютные пути в `env` действительны и у агента;
- `publish_group` в `config.toml` — **числовой первичный GID процесса агента** (у образа Hermes — 10000), а `group_add` с этим GID ставится контейнеру **службы**. `group_add` у контейнера агента не помогает: супервизоры вроде s6 сбрасывают дополнительные группы (проверено на Hermes). Без `publish_group` каталог профиля доступен только службе;
- `config.toml` должен читаться пользователем службы (uid 10051): секретов в нём нет, `chmod 0644`;
- шаг 3 (остановить старое обновление токенов) выполняется **до** снятия материалов и импорта, как и в других режимах;
- команды обслуживания: `docker compose -f compose.yaml exec keeper python3 -m sber_cert_master status|check|...`;
- проверка доступа — от пользователя агента внутри его контейнера: `docker exec <агент> su -s /bin/sh <пользователь> -c 'test -r /var/lib/sber-cert-master/public/main/token.json && echo OK'`.

## 2. Конфиг

Отредактируйте профиль `[profiles.main]` в конфиге. Значения возьмите из существующих настроек агентов (env, конфиги, переменные) или спросите человека:

- `client_id` — идентификатор сервиса из ЛК Sber API. На один `client_id` — ровно один профиль: секрет общий для client_id, конфиг с дублем не загрузится. Для второго пользователя нужен отдельный client_id;
- `env` — `prod` или `sandbox`;
- `redirect_uri` — ровно как зарегистрирован в ЛК (нужен только для входа через `auth-url`);
- `scope` — операции, которые нужны агентам (например, `openid GET_STATEMENT_ACCOUNT ...`);
- `publish_group` — в режимах system и Docker: группа пользователей агентов (в Docker — числовой GID процесса агента). Должна совпадать с группой, выбранной при установке (`AGENT_GROUP`, по умолчанию `sber-agents`); установщик уже записал её в конфиг — не меняйте без необходимости;
- `[notify]` — хотя бы один канал алертов: `command`, `webhook_url` или Telegram. Без него об истечении сроков узнают только из journald.

Если агенты уже работают с Sber API, найдите, где у них лежат `client_id`, `.p12` и секреты. Значения при этом **не выводите**: достаточно путей.

```sh
grep -rIl --exclude-dir=.git -E 'fintech(-test)?\.sberbank\.ru|client_secret|\.p12' <каталоги агентов> | head
```

Проверка: `sber-cert-master status` не выдаёт ошибку конфига; профиль показан с `initialized: False`.

### Предпроверка сертификата и секрета (до шага 3, пока старые агенты ещё работают)

Сертификат из `.p12` должен быть **привязан к client_id** в ЛК Sber API (вкладка «Сертификаты шифрования»). Новый `.p12` — сгенерировать и привязать **сейчас**, до остановки старых агентов. Проверка у банка (отправляется заведомо негодный refresh_token, ничей грант не расходуется):

```sh
sber-cert-master preflight main --p12 <client.p12> --p12-password-file <p12.pass> --client-secret-file <secret.txt>
```

| Результат | Значит | Что делать |
|---|---|---|
| `PREFLIGHT-OK` | сертификат привязан, секрет принят | дальше, к шагу 3 |
| `сертификат не привязан к client_id` | банк ответил `403 certificateNotFound` | **[ЧЕЛОВЕК]** привязать сертификат в ЛК, повторить предпроверку. К шагу 3 не переходить |
| `client_secret отклонён` | секрет неверен или истёк (сертификат при этом привязан) | **[ЧЕЛОВЕК]** взять действующий секрет (ЛК), повторить |
| ошибка сети/TLS | нет связи с банком | раздел «Неполадки», [ERRORS.md](ERRORS.md) |

## 3. Остановить старое обновление токенов

**Условия входа** (пока они не выполнены, старых агентов не останавливайте):

1. в этой сессии получен `PREFLIGHT-OK` (конец шага 2) для того самого `.p12`, который пойдёт в `init`;
2. **[ЧЕЛОВЕК]** согласовано окно переключения (~30 минут), и человек с доступом к ЛК Sber API и к конфигурации старых агентов **на месте всё это время**: он даст актуальные `refresh_token` и `client_secret` сразу после остановки (шаг 4) или выполнит вход в СберБизнес (шаг 6, вариант B);
3. известно, где у старых агентов лежит актуальный `refresh_token` и как его прочитать после остановки (файл, переменная, база), и подготовлен каталог для материалов (`$D` из шага 1);
4. шаги 3–7 выполняются одним заходом, без перерывов.

**Если на любом шаге до импорта (шаги 3–5) человек недоступен или что-то пошло не так — откатитесь:** включите обратно старое обновление токенов у агентов. До успешного импорта (шаг 6) банк ничего не израсходовал, и старая схема продолжит работать; переезд повторите позже.

Это обязательно сделать **до** того, как вы снимете материалы (шаг 4), инициализируете службу и импортируете токен. Иначе старый агент может сменить секрет или обновить токен уже после того, как вы их скопировали: служба получит устаревшие значения, а импорт упадёт с `invalid_client` или `invalid_grant`.

Для каждого агента, который ходит в Sber API:

0. В режиме system сначала убедитесь, что для каждого работающего процесса агента получено `PROCESS-OK` (шаг 1). Если агент перезапускался после той проверки, повторите её для нового pid.
1. Найдите и отключите код и задания (cron, таймеры, фоновые циклы), которые вызывают `POST /ic/sso/api/v2/oauth/token`, `change-client-secret` или `refresh-client-secret`.
2. Дождитесь завершения уже идущих запросов обновления: остановите или перезапустите агента с отключённым обновлением.
3. Подготовьте переключение кода агентов на файлы службы (шаг 7: токен из `token.json`, TLS из `tls/client.pem`), но **не включайте** его до шага 6 — файла `token.json` ещё нет. Переключение должно включаться за секунды (флаг конфигурации, перезапуск службы агента).
4. Запросы к API при этом можно не останавливать, но учтите: **успешный импорт на шаге 6 мгновенно отзывает access_token, которым агенты пользуются сейчас** (так банк ведёт себя при выдаче любой новой пары). Поэтому шаги 6 и 7 выполняются подряд, без пауз; если агентов нельзя переключить сразу, приостановите их работу с Sber API на время шагов 6–7.

Проверка: в логах и планировщиках агентов нет обращений к `/oauth/token` после отключения.

## 4. Материалы — [ЧЕЛОВЕК]

Материалы снимаются **после** шага 3, одним набором: текущий `client_secret`, дата его выпуска и `refresh_token` — те, что действуют сейчас, после остановки старых обновляльщиков. Если служба уже была инициализирована раньше, но гранта в ней нет (`refresh_token_age_days: None`, импорта не было — например, после отката), просто выполните шаг 5 заново со свежими материалами: `init` перезапишет такой профиль. `set-secret` здесь **не** используйте — ему нечем проверить секрет без гранта, он предназначен для профиля, где грант уже есть.

Попросите человека положить файлы (права `0600`, владелец — пользователь службы) в каталог `$D` из шага 1. В режиме system это делается так: `sudo install -o sber-cert-master -g sber-cert-master -m 0600 <файл> /var/lib/sber-cert-master/incoming/`.

| Файл | Где взять |
|---|---|
| `client.p12` | тот же файл, что прошёл предпроверку в шаге 2 (новый сертификат генерируется и привязывается **там**, а не здесь) |
| `p12.pass` | пароль, заданный при генерации `.p12` |
| `secret.txt` | текущий `client_secret` (ЛК Sber API или настройки агентов) |
| дата выпуска секрета | ЛК показывает срок действия. Дата выпуска = срок − 40 дней. Если даты нет, флаг не указывайте: секрет сменится при первом запуске |

Если агенты уже хранят эти файлы и пользователь службы может их прочитать, их можно использовать напрямую, без копирования.

## 5. Инициализация

```sh
sber-cert-master init main --p12 $D/client.p12 --p12-password-file $D/p12.pass \
    --client-secret-file $D/secret.txt [--secret-set-at YYYY-MM-DD]
```

Проверка: команда печатает `профиль main инициализирован; TLS до ...`. `init` сразу публикует TLS-файлы, поэтому ошибки прав или группы каталога публикации проявятся здесь, до обращения к банку. В режиме system убедитесь: `sudo ls -l /var/lib/sber-cert-master/public/main/` показывает группу агентов у `env` и `tls`.

Сразу после `init` повторите предпроверку уже с материалами службы — секрет мог смениться, пока останавливали старых агентов:

```sh
sber-cert-master preflight main     # PREFLIGHT-OK — можно импортировать
```

## 6. Токены — [ЧЕЛОВЕК]

Нужен один из двух вариантов.

**A. Refresh-токен уже есть** у агентов или выпущен в ЛК («Получить токен»). Его нужно сохранить в файл `0600`, тогда:

```sh
sber-cert-master import-refresh-token main --file $D/refresh_token.txt
```

**B. Вход пользователя:**

```sh
sber-cert-master auth-url main    # отдайте ссылку человеку
```

Человек входит в СберБизнес. Браузер перенаправит его на `redirect_uri?code=...`, и код живёт **2 минуты**. Попросите сразу передать код и тут же выполните:

```sh
sber-cert-master exchange-code main <CODE>
```

> **Момент переключения.** Как только импорт (или `exchange-code`) прошёл, старый access_token агентов отозван банком. Сразу переходите к шагу 7: запустите службу и тут же включите у агентов чтение её файлов. Проверки — потом, в шаге 8.
>
> Импортированный токен сначала проверяется у банка. Если банк явно отклонит его (`invalid_grant`), прежний рабочий токен службы останется на месте, а команда сообщит об ошибке.
>
> Если команда сообщила `403 certificateNotFound` (сертификат не привязан): **[ЧЕЛОВЕК]** привяжите сертификат к client_id в ЛК, проверьте `sber-cert-master preflight main` и повторите импорт **тем же** файлом — банк этот токен не расходовал, он сохранён в журнале. Если `invalid_client` — секрет устарел: `sber-cert-master set-secret main --file <файл с действующим секретом>` — служба сразу повторит сохранённый импорт с новым секретом.
>
> Если команда завершилась сетевой ошибкой или таймаутом, токен остаётся в журнале. **Повторите ту же команду с тем же файлом** через минуту-две, пока она не пройдёт: банк принимает повтор в течение часа. Служба на этом шаге ещё не запущена и сама повторять не будет. Другой токен в это время не импортируйте (ключ `--replace` заменяет незавершённый импорт, но прежний токен при этом теряется — используйте его, только если прежний токен заведомо негоден).

Проверка: `sber-cert-master status` показывает `access_token_valid_min` около 60, а `errors: {}`.

Затем удалите материалы:

```sh
shred -u "$D"/* 2>/dev/null || rm -f "$D"/*     # в режиме system — от пользователя службы
```

## 7. Запуск службы и переключение агентов (сразу после шага 6, без пауз)

Старый токен агентов уже отозван, а обновлять новый может только служба. Поэтому **сначала служба**, потом агенты; проверки — в шаге 8.

1. Запустите службу. При старте она сразу публикует токен (а если он истёк или не был опубликован — сначала обновляет его):

```sh
# user
systemctl --user enable --now sber-cert-master sber-cert-master-check.timer
loginctl enable-linger "$(id -un)"   # чтобы работала без входа; может потребовать [ЧЕЛОВЕК]
# system
sudo systemctl enable --now sber-cert-master sber-cert-master-check.timer
```

   Запуск службы ни от чего в агентах не зависит: если перезапуск какого-то агента ниже не удастся, служба всё равно должна работать.

   **Ворота перед переключением агентов** (обязательны на любом пути, в том числе при возобновлении): обновление токена завершено, опубликован тот же токен, что в состоянии службы, ему осталось ≥ 10 минут, и банк принимает его прямо сейчас (проверочный запрос user-info):

```sh
# system
sudo -u sber-cert-master env SBER_CERT_MASTER_CONFIG=/etc/sber-cert-master/config.toml sber-cert-master ready main
# user
sber-cert-master ready main
```

   Нет `TOKEN-READY` — службу **не останавливайте**: смотрите `status` и `journalctl -u sber-cert-master -n 50` (раздел «Неполадки», [ERRORS.md](ERRORS.md)) и повторите ворота. Агентов переключайте только после `TOKEN-READY`.

2. После `TOKEN-READY` включите у каждого агента заранее подготовленное (шаг 3) чтение файлов службы и перезапустите агента:
   - перед каждым запросом токен из `<publish_dir>/main/token.json` (поле `access_token`) или из `sber-cert-master token main` (конфиг службы агенту не нужен; при нестандартном каталоге — `--publish-dir <publish_dir>`);
   - после ответа `401` перечитать файл; если там **тот же** токен, подождать до 30 секунд, пока служба опубликует новый, и повторить запрос **один** раз;
   - mTLS: `<publish_dir>/main/tls/client.pem` (ключ и сертификат в одном файле) и `ca-bundle.pem`. Если нужны отдельные файлы — оба пути из `env` (`SBER_CLIENT_CERT`, `SBER_CLIENT_KEY`), они указывают в один неизменяемый каталог. Перечитывать при каждом новом соединении;
   - старую конфигурацию агента (`client_secret`, `refresh_token`) пока **не удаляйте** — это шаг 8.
   Не ждите, пока агент сам выполнит запрос: это проверяется в шаге 8.

## 8. Проверки после запуска

```sh
systemctl [--user] is-active sber-cert-master          # active — иначе немедленно вернитесь к шагу 7, п. 1 (запуск)
sber-cert-master check && echo OK                      # OK; «демон не работал» = служба не запущена → шаг 7
sber-cert-master token main --wait 5 >/dev/null && echo TOKEN-OK    # от пользователя службы
```

В режиме system проверьте, что опубликованное доступно **работающим процессам агентов** (а не новому `sudo -u`): группа каталога должна совпадать с группой из шага 1, и у каждого процесса агента она должна быть.

```sh
G=$(getent group sber-agents | cut -d: -f3)
[ "$(stat -c %g /var/lib/sber-cert-master/public/main)" = "$G" ] && echo DIR-GROUP-OK
for pid in <pid агента> ...; do
  awk -v g="$G" '$1=="Groups:" { for (i = 2; i <= NF; i++) if ($i == g) ok = 1 } $1=="Gid:" && $5 == g { ok = 1 } END { exit !ok }' \
    "/proc/$pid/status" && echo "PROCESS-OK $pid" || echo "НЕТ ГРУППЫ У ПРОЦЕССА $pid — исправьте немедленно (шаг 1)"
done
```

Проверка запроса от имени агента (токен идёт через stdin, а не в аргументах). Если здесь `Permission denied` — вернитесь к проверке `PROCESS-OK` из шага 1:

```sh
. <publish_dir>/main/env
printf 'Authorization: Bearer %s\n' "$(cat "$SBER_ACCESS_TOKEN_FILE")" |
  curl -q -sS --max-redirs 0 -o /dev/null -w '%{http_code}\n' -H @- --cert "$SBER_CLIENT_PEM" --cacert "$SBER_CA_BUNDLE" \
    "$SBER_API_BASE/fintech/api/v1/client-info"        # 200
```

Затем:

1. Дождитесь, пока **сам агент** (его реальный работающий процесс, а не ручная проверка) выполнит успешный запрос к банку с токеном и сертификатом службы: найдите ответ 2xx в его логах. Для агента, который запускается по расписанию, дождитесь его очередного запуска — служба уже работает и держит токен свежим.
2. Только после этого удалите из конфигурации агента `client_secret` и `refresh_token`.
3. `sber-cert-master test-notify` — человек подтверждает, что алерт пришёл.

## 9. Отчёт человеку

Сообщите:

- режим и пути (конфиг, `publish_dir`);
- `sber-cert-master status`, без секретов: эта команда их и не выводит;
- какие агенты переведены и где у них удалено собственное обновление токенов;
- канал алертов и подтверждение `test-notify`;
- даты: когда служба сменит client_secret (`client_secret_age_days` против 30 дней) и когда истекает TLS (`tls_cert.days_left`);
- что осталось сделать человеку (linger, группа, привязка будущего TLS-сертификата к client_id в ЛК).

## Обновление уже установленной службы

1. `git pull`, затем тот же установщик, что при установке (`deploy/install.sh` или `deploy/install-user.sh`), и `systemctl [--user] restart sber-cert-master`. Состояние и конфиг сохраняются, `init` повторять не нужно. Установщик кладёт новую версию в отдельный каталог `releases/<id>`, проверяет её запуск и только потом одним переименованием переключает команду `sber-cert-master`; прерванное обновление оставляет прежнюю версию рабочей. Предыдущий релиз хранится для отката.
2. Проверка: `sber-cert-master status` (`errors: {}`) и `sber-cert-master check`.
3. Если агенты были настроены на старые пути `<publish_dir>/<profile>/client.crt` и `client.key`: служба оставляет их рабочими (теперь это ссылки на актуальный сертификат), но переведите агентов на `tls/client.pem` или на пути из `env`, как описано в шаге 8, и проверьте запрос от имени агента.

## Неполадки

Полный справочник ошибок с ответами реального банка — [ERRORS.md](ERRORS.md). Кратко:

| Симптом | Действие |
|---|---|
| `нужна повторная авторизация` | повторить шаг 6 |
| `TLS: не удалось проверить сертификат банка` | `sber-cert-master update-ca`; проверить системное время |
| handshake failure / 403 `CERTIFICATE_ACCESS_EXCEPTION` | сертификат не привязан к client_id, истёк или отозван: **[ЧЕЛОВЕК]** ЛК → «Сертификаты шифрования» → выпустить и привязать новый, затем `sber-cert-master install-cert main --p12 <файл> --p12-password-file <файл>`. Команда проверяет новый сертификат у банка и обновляет токен через него, старый рабочий сертификат для этого не нужен |
| `предыдущий импорт refresh_token ещё не завершён` | ответ банка на первый импорт потерян. Если служба запущена, она повторит импорт сама; если ещё нет — повторите `import-refresh-token` **с тем же файлом**. Другой токен не импортируйте |
| отозваны и сертификат, и доступ пользователя | **[ЧЕЛОВЕК]** выпустить и привязать новый сертификат → `install-cert main --p12 ...`: команда установит сертификат и сообщит, что нужна авторизация → `auth-url main` → вход → `exchange-code main <CODE>` (запрос пойдёт уже через новый сертификат) |
| `invalid_client` | client_secret неверен или истёк: **[ЧЕЛОВЕК]** сменить его в ЛК, затем `sber-cert-master set-secret main --file <файл>` |
| `invalid_client` и одновременно нужна повторная авторизация | **[ЧЕЛОВЕК]** сменить секрет в ЛК; затем `auth-url main` → вход → `sber-cert-master exchange-code main <CODE> --client-secret-file <файл>` (код обменивается с новым секретом) |
| `не удалось взять блокировку` | другой экземпляр уже работает: `systemctl status`; второй демон не запускать |
| логи | `journalctl [--user] -u sber-cert-master -n 100` |
